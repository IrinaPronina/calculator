# План: регион объекта + контакт на выгрузке PDF

Создан: 14.09.2026
Основание: `PROJECT-KNOWLEDGE.md` (раздел 1) и разбор монетизации от 08.09.2026,
быстрая победа №1: «Регион объекта в первом экране + контакт на выгрузке PDF».

## Зачем

Сейчас расчёт нигде не сохраняется, регион не спрашивается, пользователь уходит
анонимно. Следствия:

- Конверсия считается к неправильному знаменателю: мы не отличаем расчёт в наших
  трёх областях (класс А, который можно отгрузить) от расчёта во Владивостоке.
- Нет карты спроса — того самого переговорного актива перед производителем.
- Нельзя ни продать лид соседнему дилеру, ни замкнуть петлю «расчёт → заявка».

Задача этапа — начать собирать знаменатель. Ни на одну цифру расчёта эта работа
не влияет.

## Инварианты (не нарушать)

1. **Расчёт не меняется.** Регион в первой версии НЕ участвует в ценообразовании.
   `app/domain/concrete-calc.ts` не трогаем, `npm run test:calculate-regression`
   должен проходить на текущем baseline без обновления.
2. **Деньги подрядчика не сохраняются.** В коллекцию расчётов пишем объёмы
   (м², кг, л, п.м.) и параметры объекта — и ни одного поля с ценой, наценкой или
   итогом. Личные цены — обещание продукта и одновременно красная линия из разбора.
3. **Контакт добровольный.** Скачивание PDF остаётся бесплатным и без условий;
   контакт спрашиваем только у того, кто выбрал «прислать на почту / в Telegram».
   Формулировка на сайте «бесплатно, без ограничений» не должна стать неправдой.
4. **Регион — объекта, а не пользователя.** Не гео по IP: бригады возят объекты
   через границы областей.

## Что уже есть в коде

| Место | Состояние |
| --- | --- |
| `app/page.tsx` → `components/calculator/calculator.tsx` | Серверный компонент, грузит settings, рендерит `Form` |
| `app/components/ form/Form.tsx` (807 строк) | Все поля формы в локальном `useState`, своя валидация `validateBeforeCalculate()`, по сабмиту открывает `Modal` с `PreOffer` |
| `app/components/preOffer/PreOffer.tsx` (495 строк) | Сам шлёт `POST /api/calculate`, рендерит таблицу и `PDFDownloadLink` (строка ~464) |
| `app/api/calculate/route.ts` | Stateless: rate-limit → normalize → validate → settings → расчёт → ответ. **Ничего не сохраняет** |
| `app/domain/concrete-calc.ts` | `normalizeCalculateRequest` собирает объект по белому списку полей — неизвестные поля в теле запроса молча игнорируются |
| `migrations/` | 3 миграции: user, settings, better-auth-users. Коллекции расчётов нет |

Ключевое следствие из последней строки: **лишнее поле в теле POST безопасно**.
Поэтому регион передаём НЕ внутри `CalculateRequest`, а отдельным блоком `meta` —
тогда `Required<CalculateRequest>` и `normalizedInput` в ответе не меняются, и
baseline регресс-теста остаётся валидным.

## Этап 0. Справочник регионов и зоны (0.5 дня)

`app/constants/regions.ts` — статический список субъектов РФ:

```ts
export interface Region { code: string; name: string; } // code: '52', name: 'Нижегородская область'
export const REGIONS: Region[] = [ /* 85 записей, код по ОКАТО/ГИБДД */ ];
```

Зоны — НЕ в коде, иначе каждое изменение территории = деплой. Кладём в глобальные
настройки, рядом с ценами:

```ts
// добавление в SettingsType (app/models/adminDataTypes.ts)
geo?: {
  own: string[];      // коды наших трёх областей -> зона A
  network: string[];  // коды областей сети производителя -> зона B
};                    // всё остальное -> зона C
```

Редактируется в `/edit` как и остальной глобальный шаблон (scope: 'global',
version++). Осторожно: `UserSettings extends SettingsType`, поэтому `geo` формально
окажется и в личных настройках — читать его нужно ВСЕГДА из глобального шаблона
(`getGlobalTemplate`), а не из `resolveSettingsForCalc`, иначе подрядчик в режиме
`own` сможет неявно переопределить нашу территорию. Классификация — чистая функция
`app/domain/geo.ts`:

```ts
export type Zone = 'A' | 'B' | 'C';
export const resolveZone = (code: string, geo?: SettingsType['geo']): Zone
```

Считается **на сервере** в `/api/calculate`. Клиенту зону не отдаём в первой
версии (иначе по ответу видно, как устроена наша территория).

## Этап 2. Сохранение расчёта (2–3 дня)

Новая коллекция `calculations`. Пишется в `/api/calculate` ПОСЛЕ успешного
расчёта, в try/catch — падение записи не должно ломать расчёт пользователю.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `_id` | ObjectId | |
| `createdAt` | Date | |
| `regionCode` | string | код субъекта, из `meta` |
| `zone` | 'A' \| 'B' \| 'C' | посчитана на сервере |
| `input` | object | `normalizedInput` **без цен**: area, base, thickness, preparation, concrete_grade, reinforcement*, fiber, topping, topping_amount, pump |
| `volumes` | object | объёмы только НАШЕЙ номенклатуры: `{ topping_kg, impregnation_l, sealant_m, fiber_kg, vps_m2, film_m2, fixators_pcs }` |
| `areaM2` | number | дубль `input.area` верхним полем — по нему считается «посчитано м²» |
| `userId` | string \| null | если залогинен |
| `anonId` | string | значение httpOnly-cookie `calc_aid` (uuid, 1 год) — склейка расчёта, скачивания и заявки одного человека |
| `settingsMode` | 'own' \| 'global' | для интерпретации метрик, не для цен |
| `contact` | object \| null | заполняется на этапе 3 |
| `events` | array | `[{ type, at }]`, type: `calculated` \| `pdf_downloaded` \| `pdf_sent` \| `request_sent` |

**Чего в документе НЕТ и быть не должно:** `price`, `total`, `totals`, `unitPrice`,
`pay`, любые поля из `ServiceItem` кроме `volume`. Это проверяется тестом
(см. ниже), а не только договорённостью.

`volumes` собираются из `data.section.items` по кодам нашей номенклатуры. Список
кодов — рядом с `WORK_CODES`/`MACHINE_CODES`, которые уже лежат в `PreOffer.tsx`;
вынести все три в `app/constants/item-codes.ts`, потому что серверу они теперь
тоже нужны.

Миграция `migrations/20260915000000-calculations.js`: `createCollection` +
индексы `{ createdAt: -1 }`, `{ zone: 1, createdAt: -1 }`, `{ regionCode: 1 }`,
`{ anonId: 1 }`.

## Этап 3. Контакт на выгрузке PDF (2–3 дня)

Сейчас блок кнопок — просто `PDFDownloadLink`. Становится двумя равноправными
действиями:

1. **«Скачать PDF»** — как сейчас, без единого условия. Плюс `POST /api/calc-event`
   с `{ calcId, type: 'pdf_downloaded' }` (fire-and-forget, ошибку глотаем).
2. **«Прислать на почту или в Telegram»** — открывает маленькую форму:
   переключатель канала, одно поле, чекбокс согласия, кнопка «Отправить».

Ответ `/api/calculate` дополняется полем `calcId` — без него события не к чему
привязать.

Отправка: PDF рендерится на клиенте (`@react-pdf/renderer` уже подключён), поэтому
блоб получаем через `usePDF()`/`pdf(<PDF .../>).toBlob()` и шлём в
`POST /api/calc-contact`:

```ts
{ calcId, channel: 'email' | 'telegram', value, consent: true, pdfBase64 }
```

Сервер: rate-limit (по образцу `app/utils/rate-limit.ts`, 5/час на IP), валидация
адреса, запись в `calculations.contact = { channel, value, consent, givenAt }`,
событие `pdf_sent`, отправка.

Валидация тела запроса — через `zod`, он уже в зависимостях.

Транспорты — новый `lib/mailer.ts` (**nodemailer — новая зависимость**, в проекте
его сейчас нет; SMTP Яндекса, креды в `.env`:
`SMTP_HOST/PORT/USER/PASS/FROM`) и `lib/telegram.ts` (Bot API, `TELEGRAM_BOT_TOKEN`).
У Telegram есть нюанс: боту нельзя написать первым, поэтому вместо «пришлём в
Telegram» честнее «@username для связи» — уточнить до реализации, см. открытые
вопросы. Тот же `lib/mailer.ts` переиспользуется быстрой победой №2 (кнопка заявки
письмом менеджеру), так что это не разовая работа.

**152-ФЗ.** Сбор e-mail/телеграма — персональные данные. Нужны: чекбокс согласия
(не предустановленный), ссылка на политику обработки ПДн, страница
`app/privacy/page.tsx` с текстом политики. Без этого этап не выкатывать.

## Этап 4. Метрики (1 день)

Дешевле дашборда и закрывает список «мерить с той же недели»:
`scripts/stats.mjs` — агрегация по `calculations` за период, печатает:

- расчётов всего и уникальных `anonId`;
- **доля расчётов по зонам A / B / C** и топ-10 регионов;
- доля дошедших до `pdf_downloaded`, доля с контактом (`pdf_sent`);
- посчитано м² в разрезе зон и регионов;
- объёмы нашей номенклатуры (тонны топпинга, литры пропитки) по зонам.

Добавить в `package.json`: `"stats": "node scripts/stats.mjs"`. Дашборд в `/edit` —
следующим заходом, когда будет понятно, на какие цифры реально смотрят.

## Тесты

- `npm run test:calculate-regression` — **без обновления baseline**. Это главная
  проверка инварианта 1.
- Новый `scripts/check-calculation-privacy.mjs`: прогоняет расчёт через API,
  читает записанный документ `calculations` и падает, если в нём встречается любой
  из ключей `price`, `total`, `totals`, `unitPrice`, `subtotal`, `profit`,
  `overheads`, `transport`, `rate` на любой глубине. Инвариант 2 в виде кода.
- `npm run test:calculate-validation` — дополнить кейсом «без региона → 400»,
  если решим валидировать регион и на сервере (рекомендуется: клиентская
  валидация обходится).
- `npm run test:rate-limit` — дополнить новым эндпоинтом `/api/calc-contact`.

## Открытые вопросы (решить до этапа 0)

1. **Какие три области** — конкретные коды для `geo.own`. Офис в Нижнем Новгороде;
   какие ещё две?
2. **Какие области считаем сетью производителя** (`geo.network`) — от этого
   зависит, кому вообще есть смысл предлагать «передадим дилеру в вашем регионе».
3. **Telegram как канал**: бот не может написать первым. Варианты: (а) собирать
   @username и писать руками, (б) кнопка-ссылка на бота с deep-link, после
   `/start` бот присылает PDF. Второй честнее, но это уже не 1–2 недели.
4. **Обязательность региона.** Ставим обязательным (иначе смысл теряется) —
   подтвердить, что готовы к возможной просадке доходимости до расчёта.
5. **Где живёт `calcId` до заявки** — если пользователь закрыл модалку и вернулся,
   расчёт пересчитывается и создаёт новый документ. Дедупликацию по `anonId` +
   хэшу входных параметров имеет смысл добавить сразу, иначе метрика «расчётов»
   будет завышена.
